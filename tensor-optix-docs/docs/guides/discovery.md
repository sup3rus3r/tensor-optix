# Understand your data and choose a model family (discovery)

Most modelling projects that go wrong do so before any training starts: a column that leaks the outcome, rows from the same customer on both sides of the validation split, a time series validated as if it were shuffled, or a model family that does not fit the problem. `tensor_optix.discovery` looks at your dataset with statistics before you commit to a model, and tells you what it found, how sure it is, which model family to use and why.

```python
from tensor_optix.discovery import discover

report = discover(df, target="churned")
report.to_html("discovery.html")      # a static, self-contained report
print(report.summary())               # the same content as text
```

Discovery **advises; it never changes anything on its own**. Every finding has a stable id that you accept or reject, and only accepted findings are applied when you build a model from the report.

## What a run does

1. **Profiles the target**: task type (binary / multiclass / regression / count), class balance, skew, and the metric families are compared on (AUC, macro AUC or RMSE by default).
2. **Profiles the features**: inferred type per column (numeric, categorical, datetime, identifier, text, numbers stored as text ...), missingness, constants, duplicates, collinearity, outliers.
3. **Finds the structure that decides how you must validate**:
    - *grouped* rows (several rows per customer / patient / device), detected by comparing a random split with a group split on the same model -- a random split that scores better than a group split is memorising the group;
    - *temporal* data, detected by comparing a model trained on the past with one trained on an equal-size random sample, on the same future rows (a Diebold-Mariano test);
    - a row order that carries the target (a file sorted by outcome).
4. **Keeps a confirmation holdout** (15% by default), cut with that structure -- whole groups, or the most recent rows -- before any model is chosen, and touched once at the end.
5. **Looks for leakage**: a single feature that predicts the target almost perfectly, an identifier that predicts it, missingness that predicts it, a feature equal to a future value of the target.
6. **Checks for distribution shift**: train vs `test=` rows (adversarial validation plus per-feature tests) and early vs late data.
7. **Runs cheap reference models** (dummy, linear, stump, depth-3 tree, k-NN, naive Bayes, LDA) whose relative scores describe the problem: is there signal at all, is it non-linear, does it involve interactions.
8. **Tries candidate families** on identical folds -- linear, naive Bayes, k-NN, a neural network (MLP, trained by tensor-optix until convergence) and, when installed, LightGBM and XGBoost -- and keeps adding CV repeats for the leaders while they cannot be told apart.
9. **Recommends** the simplest family that is not worse than the best one, scores it once on the holdout, and writes a plan.

## Reading the report

[Open a sample report](../assets/discovery-sample.html) (a churn dataset with a leaked column; generated by `benchmarks/validate_discovery.py`'s `churn_with_leak`). The HTML report has the same sections as `report.summary()`:

| Section | What it tells you |
|---|---|
| Summary | the recommendation, its verdict, the holdout estimate with its interval, and the findings that need a decision |
| Data understanding | the profile: columns and their inferred types, the target, the structure, quality |
| Risks | one card per finding: what was found, the evidence (test, statistic, interval, p-value), the suggested action and the exact `report.reject(...)` line to undo it |
| Families tried | every experiment with its mean score and 95% interval, and every paired comparison |
| Recommendation | the family, its configuration, why it was chosen, and the conditions it depends on |
| Plan | the steps to train it: split, preprocessing, family, monitoring |
| Limitations | what discovery could not do (budget cuts, missing optional families, no holdout) |

The JSON of the whole report is embedded in the HTML, so a saved report reloads exactly:

```python
from tensor_optix.discovery import DiscoveryReport
report = DiscoveryReport.from_html("discovery.html")
```

### The recommendation verdicts

| Verdict | Meaning |
|---|---|
| `clear_winner` | the recommended family beats every other family tried by more than the practical threshold |
| `tie_simplest_chosen` | a simpler family is *equivalent* to the best-scoring one (the whole interval of their difference lies inside the practical threshold), so the simpler one is recommended |
| `undetermined` | the best-scoring family is recommended, but some others could not be separated from it with the data and budget; they are listed as alternatives |
| `abstain` | no family beats predicting the mean / class prior by a margin that matters -- or the evidence that one does is inconclusive (the report says which). `report.build(family=...)` still builds any family you choose |

## Findings and decisions

Each finding has a severity -- `info`, `advisory`, `warning`, `critical` -- and, when there is something to do about it, a suggested action from a fixed set (`drop_column`, `set_column_type`, `use_split`, `dedupe`, `set_metric`, ...).

Some findings are *applied by default inside discovery's own experiments* (`default_applied`), because ignoring them would make every later number wrong: a detected group structure switches discovery's evaluation to a group split, a suspected leak is excluded from its experiments. That only affects how discovery measures; your model is built from the findings **you accept**.

```python
report.pending("warning")                    # findings at warning or above still undecided
report.accept("structure.grouped:col=customer_id")
report.reject("leakage.single_feature:col=refund_flag", note="known at prediction time")
report.accept_where(category="structure")    # bulk-accept by category / minimum severity
```

There is deliberately no `accept_all()`.

To re-measure with your decisions in force (for example after rejecting a leak finding you know is fine), pass them back:

```python
report2 = discover(df, target="churned", decisions=report.decisions())
```

## Building a model from the report

```python
solution = report.build()          # applies ACCEPTED findings only
solution.fit(df, target="churned")
solution.predict(new_rows)         # original labels
solution.predict_proba(new_rows)
solution.cross_validate(df, target="churned")   # re-measure with the built split
```

`build()`:

- refuses while any **critical** finding is still pending (`build(acknowledge_pending=True)` to override);
- warns, and lists the ids in `solution.evidence_mismatch`, when the findings it applies differ from the ones discovery's experiments applied -- the report's scores then do not describe this setup; re-run with `decisions=`;
- needs `build(family=...)` when the report abstained.

The solution uses the same fold-safe preprocessing discovery used: every imputation, scaling and encoding statistic is learned from training rows only, and high-cardinality target encoding is computed out-of-fold.

## Inputs

```python
discover(df, target="y")                          # pandas DataFrame (pandas is optional)
discover({"age": ..., "plan": ...}, target=y)     # dict of columns
discover(X, y, column_names=["a", "b", "c"])      # numpy arrays
discover(df, target="y", groups="customer_id")    # declare groups you know about
discover(df, target="y", time="order_date")       # declare the time column
discover(df, target="y", test=df_to_score)        # the rows the model will be used on
discover(df, target="y", column_types={"zip": "categorical_high"})
discover(df, target="y", task="regression", metric="mae")
discover(df, target="y", families=["linear", "lightgbm"])
```

| Argument | Default | |
|---|---|---|
| `budget` | `Budget.default_for_rows(n)` (about 60 s at 10k rows) | `Budget(time_s=..., max_rows=..., max_fits=...)`; discovery never silently overruns -- each cut is reported as a `budget` finding |
| `holdout` | `0.15` | fraction kept aside to confirm the recommendation; `0` disables it |
| `seed` | `0` | the run is reproducible given the seed |
| `store` | `None` | an `ExperimentStore` (or a ledger path) to record the run in |
| `verbose` | `False` | print progress |

Install the optional pieces as needed:

```bash
pip install "tensor-optix[pandas]"            # DataFrame input
pip install "tensor-optix[discovery-boost]"   # LightGBM and XGBoost candidates
```

Without LightGBM / XGBoost the report says so -- at `advisory` severity when the reference models show non-linear structure, where boosted trees are often the strongest tabular family.

## Recording runs in the ledger

```python
from tensor_optix.ledger import ExperimentStore
report = discover(df, target="churned", store=ExperimentStore("runs.db"))
report.ledger_refs     # {"experiment_id": ..., "trials": {...}}
```

A parent experiment (`algorithm="discovery"`) with one child per family trial, plus events for the profile (versioned meta-features), every finding, the decisions, the recommendation and the budget. These records live under their own `discovery:<data fingerprint>` task name, so they never count as evidence for other tasks, and discovery never reads ledger history to make a decision.

## What discovery does not do (yet)

- Reinforcement-learning environments: `discover(env)` raises a clear error; RL discovery is planned.
- Unsupervised data (no target).
- Feature-engineering recommendations (which kinds of features are worth adding) are planned as a separate stage.

See [Discovery statistics](discovery-statistics.md) for exactly how each test and comparison works, and the [reference](../reference/discovery.md) for the full API.
